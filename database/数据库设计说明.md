## 关系数据库设计

本设计将诊所、医生、患者、排班、预约、就诊、结算及授权等对象映射为PostgreSQL关系表。每条业务记录以独立UUID标识，关系通过外键维护；预约编号和单据编号用于业务检索，不替代主键。数据字典依据当前工程模型，包含32个领域模型，框架会话、迁移及权限连接表另由Django管理。

## 类与关系表的映射

实体类形成基础表，类的属性形成字段；对象的方法由事务服务执行，不作为数据库字段保存。边界对象和控制对象承担界面及请求协调职责，无须逐类建表。PerformanceReport按授权范围查询收款、成本及预约记录生成，不建立可任意修改的汇总总数表。

| 分析关系 | 关系模型 | 完整性规则 |
|---|---|---|
| 医生与诊所的多对多服务关系 | domain_dentistclinic连接两张基础表，并保存服务期 | 同一医生在同一诊所的有效服务期不得重叠 |
| 医生与资质的多对多关系 | domain_dentistqualification保存证号与有效期 | 医生、资质类型、证号联合唯一 |
| 患者与过敏类型的多对多关系 | domain_patientallergy保存表现与备注 | 患者和过敏类型联合唯一 |
| 一个患者有多个联系人 | domain_emergencycontact.patient_id | 联系人有独立主键，patient_id不能单独作为主键 |
| 一次预约最多一次就诊 | domain_visit.appointment_id唯一外键 | 保留预约与就诊之间的直接追溯关系 |
| 一次就诊有多项治疗 | domain_visittreatment.visit_id | 明细独立UUID，visit_id可重复 |
| 一张结算单有多个项目 | domain_invoiceline.invoice_id | 明细独立UUID；同单据同治疗来源唯一 |
| 一张单据可有多次支付尝试 | domain_paymentrecord.invoice_id | 最多一条成功记录 |
| 一个账号可有多项角色授权 | domain_roleassignment | 角色、范围、诊所与有效期分别记录 |

上述明细与主单关系不意味着正式业务记录应级联删除。患者、就诊、单据等采用停用、作废与历史保留；数据库外键防止孤立记录。

## 主键 外键与规范化

使用独立主键避免将姓名、手机号或可变编号作为引用身份。多对多关系拆成连接表，一对多关系在“多”的一端设置外键。金额使用定点数，时间使用带时区时间戳，成本发生日使用日期。

医生、诊所等公共资料只在基础表维护，预约通过排班取得诊所与医生。排班保留医生及诊所字段用于跨诊所时间排斥，并以复合外键保证其与服务关系一致。治疗和结算明细保存名称、数量与价格快照，以保持历史业务事实；目录调价不能改变旧单金额。该快照属于有意保留的历史数据，不与当前目录自动同步。

## 约束与事务

| 层次 | 已实现的措施 |
|---|---|
| 数据库结构 | 主键、外键、非空、业务编号唯一、条件唯一索引 |
| 数据库时间关系 | 半开区间[start,end)排斥约束防止医生跨店重叠排班 |
| 数据库金额与状态 | 正数量、非负价格、正确小计和合法状态检查 |
| 跨对象业务 | 事务中核验权限、状态、版本、患者重叠预约及就诊完成条件 |
| 重复请求 | 请求回执与业务结果同事务保存，相同请求返回同一结果 |
| 历史保护 | 已引用排班身份不可任意修改；审计日志只追加 |

创建预约先锁患者，再按稳定顺序锁诊所、医生、连续排班和资源；在同一事务中重新检查治疗时长、周转、患者重叠和资源峰值，并保存预约、占用与审计。出单、付款、作废及更正按就诊至单据的顺序锁定，避免付款和作废同时成功。普通CHECK不能表达跨表总和或所有业务条件，相关条件由事务服务核验。

## 连续预约与资源实现

0003与0004迁移已将七类预约资源模型安装为运行数据库表，并为既有预约补充方案和时段关联。Appointment.slot保留首个单元，AppointmentSlot记录全部连续单元及历史版本；有效单元关联由条件唯一约束保护。每个扩展模型使用独立UUID主键，AppointmentPlan.appointment_id与TreatmentBookingProfile.treatment_type_id为唯一外键。

治疗预计时长与清洁周转分别配置。预计45分钟需连续两个30分钟排班单元；医生和患者按治疗区间核对，牙椅、设备与辅助人员占用延续至清洁周转结束。这是计算示例，不代表真实治疗的标准时长。治疗类型未明确时安排30分钟咨询，仍检查牙椅容量。演示资源配置仅为虚构测试值，不能作为调研门店容量。

资源容量按半开区间的起止事件扫描计算峰值，同时计入有效预约占用及部分停用数量。相邻区间不叠加；同一事务锁定相关资源后再校验，避免并发争用超额。数据库CHECK负责单行合法性，跨记录容量由统一事务服务保护。

改约先核验新安排，再使旧单元与旧资源占用失效并保存新版本；失败则全部回滚，旧安排保留。取消和明确核实的爽约释放有效占用但保留历史。治疗延长通过同一校验流程，后续时段或资源冲突时拒绝延长，前台先协调受影响预约。

新增资源停用区间不会自动取消患者预约。资源协调页列出重叠的待到诊或已到诊记录，前台据此联系患者；接诊入口重新检查资源是否可用。降低容量或直接停用会破坏已有占用时拒绝普通参数变更。误签到在尚未建立就诊时可经前台记录核验依据后纠正；已经接诊须走受控更正。

## 患者身份与联系方式

患者UUID是稳定身份，手机号是有索引的可变联系方式，已取消唯一约束。相同手机号或姓名与出生日期匹配仅提供重复提示，不自动合并、不转移病历，也不据此判定新客优惠资格。自助注册形成独立待核验档案；前台先建档后，可在本人核验入口关联未占用账号或创建新的自助账号。

本人核验保存核验岗位、时刻及审计依据。手机号变更由前台核验后办理，患者身份与原就诊关系保持不变；姓名或出生日期修改会使旧身份核验失效。账号已关联其他档案时拒绝直接绑定。跨诊所手机号查询仅显示基础识别信息，不开放病史、联系人和账单地址。

辅助人员以诊所容量池表示，尚未实现具体护士身份、跨店个人排班和资质组合。团购外部核销、真实支付与退款不属于本演示实现；付款为模拟记录。项目性能目标仍须单独测量，不能由功能测试推定。

## 经营统计口径

采用自然季度，收入按成功收款时刻归属，成本按发生日归属。医疗用品与运营费用分别汇总；未归属医生的公共费用单列，不自动分摊。医生报表显示扣除直接成本后金额，不将其称为个人净利润。全连锁季度基金为max(管理口径净利润,0) × 10%，四舍五入至分，个人分配规则尚未确定。

取消率与爽约率使用同一到期预约范围，按首个单元开始时刻归入季度、按计划治疗结束判断到期；旧记录无方案时使用首单元结束。未确认到期记录保持待核对，不自动记为爽约。利用率按全部连续时段关联统计，分子为已到诊或已完成预约关联的到期单元，分母为已结束的有效排班单元。
