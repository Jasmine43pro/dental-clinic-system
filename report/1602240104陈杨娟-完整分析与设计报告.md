# A 业务建模

## A1 愿景

本报告围绕牙科诊所预约、到诊、诊疗、结算及经营管理展开。通过岳雅口腔医院实地调研，识别患者服务链路中的信息交接要求；以Andrew Dental Chain为设计对象，形成业务模型、系统需求、分析模型与关系数据库设计，并说明系统实现中的权限和业务状态控制。系统建设的目标是减少重复核对、统一资源与费用记录，并支持按权限追溯业务来源。

Andrew Dental Chain（ADC）是本项目的设计对象。课程案例记载，ADC在广东设有15家牙科诊所，计划在未来三年扩大至约30家。各诊所日常运营主要依赖总部人工监督，管理层需要统一掌握患者就诊与取消情况、医生资质、治疗费用及季度经营数据。本项目拟通过统一业务记录和统计口径，改善预约协调、费用核对及经营汇总过程。

| 项目 | 内容 |
| --- | --- |
| 系统 | 牙科诊所管理系统 |
| 目标组织 | Andrew Dental Chain（ADC）及其所属牙科诊所。系统服务于连锁管理层、诊所工作人员与患者。 |
| 负责人 | 业务负责人：Andrew Chen，ADC案例首席执行官兼首席牙医，提出经营目标并作出业务决策。<br>课程项目负责人：陈杨娟，负责分析与设计。 |
| 目标 | G1 减少预约确认与变更中的重复沟通工作量。G2 缩短治疗完成后费用明细核对所需时间。G3 减少季度经营汇总与差异核对所需人工工时。 |
| 度量 | G1为预约确认及变更人工分钟/笔；G2为同类费用核对分钟/笔；G3为期间经营汇总人工小时。试用时采集同口径基线与结果，业务体验时长不等于岗位操作工时。 |
| 当前基线与改进目标 | 基线按调研计时或业务记录统计；目标按相同业务类型与工作量确定。G1、G2采用分钟/笔，G3采用人工小时/统计期间。实际运行效果在系统试用后按同口径评价。 |

指标采用可比工作量和服务类型，并区分患者等待、实际诊疗与工作人员处理时间。节省处理时间不直接等于减少人员工资；系统维护、培训和数据整理也会产生成本。

预约处理工时按完整处理笔数计算，费用核对按同类治疗项目比较，季度汇总按参与人员的实际投入求和。改进幅度按（基线值－试用值）÷基线值计算，基线与试用结果采用相同的计时起止点和工作量范围。

评价系统效果时，同时记录资料整理、岗位培训、维护与异常处理的时间投入，避免仅以页面操作速度推算经营效益。季度汇总覆盖的诊所数量、单据范围和补录情况应保持可比。

### A1.1 业务范围

拟支持患者档案、医生与诊所资料、资质登记、服务关系、排班、预约、签到、诊疗记录、结算、成本与经营统计。患者可以自助预约，也可由前台代办；诊疗判断由医生负责。

本项目当前拟实现的可运行演示版本采用全额模拟收款，即记录支付方式、金额与状态，不发生真实资金交易。该版本不接入真实支付、税控发票、医保及完整退款；医学影像、完整药品库存、工资税务和家属代约暂不纳入实现范围。

预约可行性由医生时间、治疗预计时长以及所需牙椅、设备和辅助人员共同决定。系统按项目维护预计时长、资源组合及周转时间，诊所管理者依据服务安排配置容量和停用区间。治疗类型未明确时先安排咨询，由医生评估后确定后续治疗安排。演示系统以30分钟为排班单元，项目时长和周转时间分别配置。

### A1.2 实地调研与设计对象

2026年10月5日上午，我到岳阳市岳雅口腔医院开展实地调研，以“工作日大学生超声波基础洁牙”团购服务为观察入口，通过电话预约、微信沟通、本人到店体验、现场观察及候诊、准备及服务结束时的简短访谈，梳理预约至服务结束的完整链路。接触岗位包括前台、咨询人员、接诊医师及护士（助手），访谈内容按岗位和业务事项归纳。

调研对象岳雅口腔医院为岳阳市单院区私立二级口腔医院，位于南湖新区求索西路湖畔新村1栋106号，接诊时段为8:30—18:00。调研记录的院区面积约2200平方米，牙椅20张，普通诊室18间、儿童诊室2间。医院总配置与当日可用资源分别登记，预约容量依据实际开放资源确定。

岳雅口腔医院是本次实地调研的单院区样本；ADC是课程案例中的连锁系统设计对象，不属于本次实地调研范围。调研提供团购预约、到诊核对、医护交接和服务核销的业务依据；ADC案例提供15家诊所及总部管理的设计背景。总部、跨店医生和连锁激励基金属于ADC分析范围，院区规模、接诊时间和团购规则按机构分别配置。

系统定位与服务对象：本项目设计的是支持牙科连锁组织业务管理的信息系统，连接患者、前台、医生、诊所管理者、总部管理者和财务。它为患者提供预约与记录查询，为工作人员提供业务记录和核对支持，为管理层提供跨诊所的统一统计与追溯依据；诊疗判断仍由医生作出。

本次购买的是工作日大学生超声波基础洁牙套餐，凭学生证、限本人一次使用，服务内容包括初诊检查、龈上超声洁治、冲洗及抛光，不包含喷砂。套餐资格、包含与排除项目在预约和到院时核对；

本次调研的核心发现是买券、预约确认、到诊、服务完成、券核销和商家到账属于不同业务事件。我在调研后填写了一份调研问卷，本次未出现预约冲突，因此改进方案的重点在于信息关联和交接清晰。

| 治疗目录与价格 | 总部授权录入，总部管理者批准，按版本生效 | ADC价格治理与历史快照方案 |

# B 需求

## B1 系统参与者与权限

系统边界为牙科诊所管理软件。业务工人在与软件交互时成为系统执行者；同一人员可能承担多个岗位，实际授权按职责和数据范围区分。

| 执行者 | 主要操作 | 权限边界 |
| --- | --- | --- |
| 患者 | 维护本人允许修改的资料，自助预约、取消及查询本人记录。 | 不出单、不登记收款、不维护医生资质。 |
| 前台 | 患者建档、代约、调整取消、签到、生成结算及模拟收款。 | 限所属诊所；不修改诊断，不查看利润或个人激励。 |
| 医生 | 查看本人排班、接诊、记录治疗、申请更正及查看本人业绩。 | 只读本人资质；不维护目录价格，不审批本人更正。 |
| 诊所管理者 | 维护本诊所资料、安排排班、审批更正及查询本诊所经营。 | 审批不等于代写诊断；不能任意修改他诊所资料。 |
| 总部管理者 | 管理连锁诊所、医生、资质与服务关系，查询连锁经营。 | 业务职责不自动授予全部病历编辑权限。 |
| 财务 | 核对结算、按授权作废未支付单据、记录成本及核对统计。 | 不得修改诊疗内容；按诊所或全局财务授权访问。 |
| 系统管理员 | 管理账号、角色和数据范围，查询获授权的运行审计。 | 技术身份不自动取得全部医疗或经营资料。 |

系统支持人员兼岗，权限仍按任务与数据范围授予。申请更正、审批更正、作废单据和授权管理分别设置权限；更正申请人不得审批本人申请，必要时由上级授权岗位复核。

## B4 核心用例规约

规约采用执行者、前置条件、后置条件、涉众利益、基本路径、扩展、字段列表、业务规则、质量需求和设计约束的结构。触发事件与最小保证单独说明。

用例规约规定ADC本系统的目标行为。岳雅样本通过电话或微信确认到店时段，并按现场进度接诊；演示系统采用30分钟排班单元。提前2小时自助取消、更正审批及总部维护目录属于系统配置与治理方案，分别与样本流程衔接。

### B4.1 UC-03 创建预约

| 项目 | 规约 |
| --- | --- |
| 执行者、触发 | 患者本人或授权前台提出预约请求；P0 |
| 涉众利益 | 患者获得准确安排；前台避免重档和重复录入；医生不被重叠预约；管理者获得一致的业务记录 |
| 前置条件 | 登录账号有效；患者已关联或由前台选定；诊所启用；目标医生服务关系和排班有效。有效性在提交时再次检查 |
| 成功后置条件 | 创建唯一编号、状态待到诊的预约，关联一个患者和一个或多个连续排班单元；记录来源、操作者与时间 |
| 最小保证 | 失败不占用新时段、不改变已有预约；重复同一请求不产生第二条记录 |

基本路径：

1. 患者或前台提交患者身份、诊所、日期及医生筛选条件。

2. 系统验证本人或代办范围，返回可选医生与有效可预约时段。

3. 患者或前台提交所选时段及可选预约原因。

4. 系统核对营业时间、服务关系、排班、治疗时长、所需资源及医生与患者的重叠预约，反馈预约摘要。

5. 患者或前台确认预约摘要。

6. 系统再次校验权限、有效性和冲突，保存预约、来源及审计信息。

7. 系统向发起者反馈编号、诊所、医生、开始与结束时间；代办时前台告知患者。

### 扩展路径与补充约束

| 扩展点 | 条件与处理 | 恢复位置或终止结果 |
| --- | --- | --- |
| 1a | 前台未找到患者：先按UC-01建档并核对去重 | 前台完成建档后回到1；失败时系统不创建预约 |
| 2a | 无时段、医生服务关系失效或选择过去时间 | 系统返回原因；患者或前台可重新选择 |
| 4a/6a | 医生或所需资源已占用、预计时长不符，或患者已有重叠有效预约 | 系统不保存；仅反馈当前角色有权查看的冲突摘要，回到2 |
| 6b | 相同请求重复提交 | 系统返回同一结果；相同请求标识但内容不同则拒绝冲突 |
| 6c | 保存失败或确认期间排班失效 | 系统不产生预约和占用，反馈可理解的重试提示 |
| 任一步 | 无权限或会话失效 | 系统拒绝操作，不泄露患者或时段的敏感关联 |

| 字段 | 要求 |
| --- | --- |
| 患者、排班单元 | 必填；排班单元确定诊所与医生，预约起止时间覆盖预计治疗时长；记录所需资源及占用时段。 |
| 预约原因 | 可选；不能替代医疗诊断 |
| 预约编号、来源、创建人、创建时间 | 系统生成；来源区分患者自助与前台代办 |
| 预约状态 | 系统维护，初始为待到诊 |

业务规则：演示版本以30分钟为排班单元，治疗按预计时长占用连续单元，并单独校验周转和资源占用；同一医生跨诊所及同一患者的有效预约不得重叠。手机号用于检索与重复提示，变更号码或不同账号不能直接认定为新患者；档案关联须结合本人核验。购买团购券不直接创建已确认预约；查询结果不占用资源，最终确认再次校验。

质量需求：并发抢同一时段仅允许一次成功；失败原因可理解；操作可审计。查询与校验2秒目标的测试条件及验收方法见B7节。设计约束：Web入口共用业务规则；不接入真实消息发送；冲突控制在服务端生效。

### B4.2 UC-06 完成就诊并记录治疗

| 项目 | 规约 |
| --- | --- |
| 执行者、触发 | 预约指定医生接诊已签到患者；P0 |
| 涉众利益 | 患者资料与治疗准确；医生获得必要过敏提示；前台和财务使用同源收费明细 |
| 前置条件 | 医生账号有效且属于本次预约；预约已到诊；必要患者资料可按权限读取 |
| 成功后置条件 | 唯一关联就诊为已完成，至少一项治疗明细；预约同步完成；保留价格快照、医生和完成时间 |
| 最小保证 | 完成失败保留已保存草稿，预约和就诊不错误完成，不生成结算单 |

基本路径：

1. 医生请求接诊指定预约。

2. 系统验证权限、签到状态及关联唯一性，反馈必要患者信息、过敏和特殊需求。

3. 医生确认已核对必要信息并请求开始就诊。

4. 系统建立或返回同一进行中就诊，记录开始时间。

5. 医生提交诊疗说明、治疗项目、数量及必要备注。

6. 系统验证项目与数量，保存项目名称和目录单价快照，计算小计并反馈明细。

7. 医生对其他治疗重复第5—6步，核对完整记录后请求完成。

8. 系统校验说明与至少一项有效明细，保存完成版本与审计，同步预约为已完成并反馈结果。

### 扩展路径与补充约束

| 扩展点 | 条件与处理 | 结果 |
| --- | --- | --- |
| 2a | 未签到或当前医生不匹配 | 系统拒绝开始；医生联系前台核实，不擅自转移接诊医生 |
| 2b | 已存在进行中记录 | 系统向有权医生反馈原记录；已完成则只读或走更正，不新建第二次 |
| 5a/6a | 项目停用、数量不大于零或价格不合法 | 系统拒绝新增明细，说明字段错误；历史明细保留可读 |
| 5b | 过敏信息有疑问 | 医生记录核实情况；未记录不等于确认无过敏 |
| 7a | 医生暂存并稍后继续 | 系统保留进行中状态，不生成结算单 |
| 8a | 没有治疗明细或必要说明 | 系统拒绝完成，医生补充记录 |
| 完成后 | 原医生提出更正与理由，管理者审批 | 系统保留原值、新值和版本；审批前不生效；衔接见B6节 |
| 保存时 | 系统保存失败 | 系统不宣告完成，不丢弃已保存内容 |

| 字段 | 要求 |
| --- | --- |
| 关联预约、负责医生 | 固定关联；患者和诊所从预约确定 |
| 开始时间、完成时间 | 分别在开始、完成时记录；完成前无完成时间 |
| 诊疗说明、特殊需求 | 说明在完成时必填；特殊需求按实际记录 |
| 治疗项目、数量、名称和单价快照 | 项目有效、数量大于零；医生不能自行改价 |
| 就诊版本及更正理由 | 完成与更正可追溯，审批核对基准版本 |

业务规则：进行中可无治疗，完成时至少一项；演示版本每次就诊设置一名负责医生，同时允许记录护士或助手等参与岗位。完成记录进入受控更正。质量需求：金额可复算、访问与更正可追溯、越权被拒绝。设计约束：系统保存诊疗记录，不替代医疗决策；医学影像和签到后的换医生流程列入后续扩展。

### B4.3 UC-07a 生成结算单

| 项目 | 规约 |
| --- | --- |
| 执行者、触发 | 前台提出为已完成就诊生成结算单的请求；P0 |
| 涉众利益 | 患者知道各项费用；前台无需重录；医生记录不被收费人员改写；财务可追溯 |
| 前置条件 | 前台有本诊所结算权限；就诊已完成且至少有一项有效治疗；没有待处理更正与另一张未作废单据 |
| 成功后置条件 | 生成唯一编号、状态已出单的结算单及完整明细快照；总价可复算；此时尚未确认收款收入 |
| 最小保证 | 失败不留残缺单据、不修改诊疗明细、不计入收入 |

基本路径：

1. 前台请求为指定已完成就诊办理结算。

2. 系统校验权限、就诊状态、更正情况及有效单据唯一性。

3. 系统反馈当前有效版本的治疗名称、数量、单价、小计及总价。

4. 前台与患者核对费用并提交出单确认。

5. 系统再次核对版本、权限和唯一性，保存新编号、来源版本、明细快照、出单人与时间。

6. 系统向前台反馈结算单。财务核对和患者本人查询分别由UC-07b、UC-07d处理。

### 扩展路径与补充约束

| 扩展点 | 条件与处理 | 结果 |
| --- | --- | --- |
| 2a | 就诊未完成、无明细或更正待审批 | 系统拒绝出单，指出需先完成的业务 |
| 2b/5a | 已有未作废单据或重复提交 | 系统返回已有合法单据，不重复出单 |
| 4a | 发现诊疗明细有误 | 前台暂停出单，由原医生申请更正；前台不能直接改治疗 |
| 5b | 确认前版本已变 | 系统停止出单，重新反馈明细并核对 |

## B6 关键业务规则

| 编号 | 规则 |
| --- | --- |
| R01 预约与到诊 | 一个预约对应一名患者、一家诊所、一名医生和一个或多个连续排班单元；同一医生跨店、同一患者均不得存在重叠有效预约。一个预约最多形成一次就诊。 同时按治疗预计时长校验所需牙椅、设备和辅助人员，避免资源超出容量或处于不可用状态。资源种类及容量按诊所配置进行校验。 |
| R02 取消与未到 | 患者至少提前2小时可自助取消；不足2小时但未开始由前台处理。开始后不走普通取消。预约结束后由前台核实未到，不能仅凭未签到自动判为爽约。 |
| R03 完成与更正 | 就诊开始时可无治疗明细，完成时至少一项。完成后由原医生申请、诊所管理者审批更正，历史保留。 |
| R04 出单前更正 | 无待审批更正且治疗核对完成才允许出单；批准后按新版本，驳回后按原有效版本办理。 |
| R05 已出单未付更正 | 需要改变收费时先受控作废旧单，再审批及重开新编号；保存替代关系。处理中旧单不能收款。 |
| R06 已支付后 | 不得作废或改变收费；只允许审批补充不影响收费的诊疗说明。本课程演示版本不实现完整退款。 |
| R07 结算与收款 | 一次就诊最多一张未作废结算单；单据可有多次尝试但最多一次成功收款。价格快照保留，目录变价不修改历史。 |
| R08 统计 | 取消率和爽约率使用同一到期预约批次，包含已取消记录。服务开始时间在统计期间且结束时间不晚于截止时刻；待核对单列，分母为零反馈暂无数据。 |
| R09 成本与基金 | 按自然季度统计；收入按成功收款时刻、成本按发生日，未支付列应收。管理口径净利润＝收款收入－用品成本－相关运营费用。全连锁基金＝max(净利润,0)×10%，个人分配不自动计算。 |

业务规则为系统分析与验收提供统一约定。涉及现状制度的资料按来源登记，涉及系统配置的数值保留参数版本，变更时评估其对预约、历史单据和统计口径的影响。

公共费用按诊所归集，采用批准的规则进行分摊，跨期补录列示差异；个人奖金与连锁基金分别处理。误签到、未到纠错、手机号变更和临时停诊按授权办理，保存核验依据和操作记录。

## B7 质量需求与约束

| 类别 | 要求 | 核对方法 |
| --- | --- | --- |
| 权限 | 同一业务记录按本人、本诊所或全连锁授权访问，直接访问同样受控。 | 分别核对允许操作、拒绝操作及敏感字段。 |

易用模式由使用者主动选择，不按年龄强制开启。朗读由使用者主动触发并可停止，不自动朗读病历或身份资料；不可用时仍保留文字及前台联系渠道。具体页面布局不写入用例基本路径。

响应性能验收设定15家诊所、10万条预约和20个并发用户的测试规模，查询及详情加载的95百分位响应时间目标不超过2秒。易用性验收至少安排5名测试者，各完成预约和关联查询两项任务，按10次任务计算完成率，目标不低于90%；记录错误类型、网络与测试设备条件。系统验收与实地调研的业务测量分别开展。

# C 分析

分析模型把系统用例落实到对象责任与协作，说明业务信息由哪些类保存、规则由哪些对象保护，以及关键对象在事件发生后如何改变状态。模型使用边界、控制、实体三类职责；图中的操作表达业务责任，属性表达业务事实，关联表达对象之间的稳定联系。

## C4 异常路径与跨对象一致性

| 场景 | 受保护对象与处理 |
| --- | --- |
| 重复或并发预约 | Appointment、AppointmentSlot及ResourceOccupancy一起确认或一起失败；原请求重试返回同一预约，失效时段不产生残留占用。 |
| 改期与取消 | 先判断旧预约允许操作，再核验新安排；改期失败保留旧占用，成功后释放旧占用并保留差异。取消释放占用并留存原记录。 |
| 误签到及未到核对 | 未建立就诊时按授权纠正误签到；已接诊后涉及医疗记录的纠错走受控处理。预约到期且联系未确认仍列待核对，不自动爽约。 |
| 出单前更正 | 原医生提出申请，待审批期间暂停出单；批准后按新版本，驳回后按原版本办理。 |
| 未支付单据更正 | 收费变化先作废原未付单，再审批更正，重开使用新编号和替代关联；原单快照及作废原因保留。 |
| 已支付记录更正 | 拒绝改变收费和作废；只允许不影响收费的补充说明。完整退款作为另行扩展的业务流程。 |
| 收款与作废竞争 | Invoice检验当前状态，PaymentRecord约束最多一次全额成功；成功收款与作废不能同时成立。 |
| 关联导航 | 源预约及关联就诊分别核验访问权限；空关系提示尚无就诊，无权限不得伪装无记录或泄露详情。 |
| 授权或目录变化 | 最终确认重新核验当前权限和有效版本；历史目录价、已完成记录及已出单快照保持原值。 |

# D 数据库与实现设计

本部分将分析模型映射为关系表，并说明事务服务、岗位授权和界面状态的实现方式。数据字典对应当前Django与PostgreSQL工程；设计案例与实地调研样本仍按前文区分，演示数据不作为真实经营数据。

## D1 设计范围与数据组织

本设计将诊所、医生、患者、排班、预约、就诊、结算及授权等对象映射为PostgreSQL关系表。每条业务记录以独立UUID标识，关系通过外键维护；预约编号和单据编号用于业务检索，不替代主键。数据字典依据当前工程模型，包含32个领域模型，框架会话、迁移及权限连接表另由Django管理。

## D2 类与关系表的映射

实体类形成基础表，类的属性形成字段；对象的方法由事务服务执行，不作为数据库字段保存。边界对象和控制对象承担界面及请求协调职责，无须逐类建表。PerformanceReport按授权范围查询收款、成本及预约记录生成，不建立可任意修改的汇总总数表。

| 分析关系 | 关系模型 | 完整性规则 |
| --- | --- | --- |
| 医生与诊所的多对多服务关系 | domain_dentistclinic连接两张基础表，并保存服务期 | 同一医生在同一诊所的有效服务期不得重叠 |
| 医生与资质的多对多关系 | domain_dentistqualification保存证号与有效期 | 医生、资质类型、证号联合唯一 |
| 患者与过敏类型的多对多关系 | domain_patientallergy保存表现与备注 | 患者和过敏类型联合唯一 |
| 一个患者有多个联系人 | domain_emergencycontact.patient_id | 联系人有独立主键，patient_id不能单独作为主键 |
| 一次预约最多一次就诊 | domain_visit.appointment_id唯一外键 | 保留预约与就诊之间的直接追溯关系 |
| 一次就诊有多项治疗 | domain_visittreatment.visit_id | 明细独立UUID，visit_id可重复 |
| 一张结算单有多个项目 | domain_invoiceline.invoice_id | 明细独立UUID；同单据同治疗来源唯一 |
| 一张单据可有多次支付尝试 | domain_paymentrecord.invoice_id | 最多一条成功记录 |
| 一个账号可有多项角色授权 | domain_roleassignment | 角色、范围、诊所与有效期分别记录 |

上述明细与主单关系不意味着正式业务记录应级联删除。患者、就诊、单据等采用停用、作废与历史保留；数据库外键防止孤立记录。

## D3 主键 外键与规范化

代理主键和业务唯一性分别处理。UUID承担稳定的引用身份；单据号、资质证号以及关联对象组合按业务需要设置唯一约束。明细表使用独立UUID，并以主单据外键和来源对象的联合唯一约束避免重复来源；主键负责标识明细，业务唯一约束负责防止重复来源；两者分别承担记录识别与业务完整性职责。

结算单替代关系是已有的自引用。domain_invoice.replaces_id允许为空并唯一引用domain_invoice.id，新单据指向被替代的旧单据；无前序单据时为空。该关系形成受控更正中的替代链，保留原单据、作废依据和前后引用关系，支持结算更正的完整追溯。

| 关系 | 表和引用字段 | 约束与用途 |
| --- | --- | --- |
| 主单与明细 | domain_invoiceline.invoice_id → domain_invoice.id | 一对多；同单据与治疗来源联合唯一 |
| 结算单替代链 | domain_invoice.replaces_id → domain_invoice.id | 可空唯一外键；新单引用被替代旧单 |
| 账号与岗位 | domain_roleassignment.user_id及role_id | 支持兼岗，另记录范围与有效期 |
| 角色与权限 | domain_role.permissions连接框架Permission | 框架维护关联表；业务入口重新授权 |

使用独立主键避免将姓名、手机号或可变编号作为引用身份。多对多关系拆成连接表，一对多关系在“多”的一端设置外键。金额使用定点数，时间使用带时区时间戳，成本发生日使用日期。

医生、诊所等公共资料只在基础表维护，预约通过排班取得诊所与医生。排班保留医生及诊所字段用于跨诊所时间排斥，并以复合外键保证其与服务关系一致。治疗和结算明细保存名称、数量与价格快照，以保持历史业务事实；目录调价不能改变旧单金额。该快照属于有意保留的历史数据，不与当前目录自动同步。

## D4 约束与事务

| 层次 | 已实现的措施 |
| --- | --- |
| 数据库结构 | 主键、外键、非空、业务编号唯一、条件唯一索引 |
| 数据库时间关系 | 半开区间[start,end)排斥约束防止医生跨店重叠排班 |
| 数据库金额与状态 | 正数量、非负价格、正确小计和合法状态检查 |
| 跨对象业务 | 事务中核验权限、状态、版本、患者重叠预约及就诊完成条件 |
| 重复请求 | 请求回执与业务结果同事务保存，相同请求返回同一结果 |
| 历史保护 | 已引用排班身份不可任意修改；审计日志只追加 |

创建预约先锁患者，再按稳定顺序锁诊所、医生、连续排班和资源；在同一事务中重新检查治疗时长、周转、患者重叠和资源峰值，并保存预约、占用与审计。出单、付款、作废及更正按就诊至单据的顺序锁定，避免付款和作废同时成功。普通CHECK不能表达跨表总和或所有业务条件，相关条件由事务服务核验。

## D5 连续预约与资源实现

0003与0004迁移已将七类预约资源模型安装为运行数据库表，并为既有预约补充方案和时段关联。Appointment.slot保留首个单元，AppointmentSlot记录全部连续单元及历史版本；有效单元关联由条件唯一约束保护。每个扩展模型使用独立UUID主键，AppointmentPlan.appointment_id与TreatmentBookingProfile.treatment_type_id为唯一外键。

治疗预计时长与清洁周转分别配置。预计45分钟需连续两个30分钟排班单元；医生和患者按治疗区间核对，牙椅、设备与辅助人员占用延续至清洁周转结束。这是计算示例，不代表真实治疗的标准时长。治疗类型未明确时安排30分钟咨询，仍检查牙椅容量。演示资源配置仅为虚构测试值，不能作为调研门店容量。

资源容量按半开区间的起止事件扫描计算峰值，同时计入有效预约占用及部分停用数量。相邻区间不叠加；同一事务锁定相关资源后再校验，避免并发争用超额。数据库CHECK负责单行合法性，跨记录容量由统一事务服务保护。

改约先核验新安排，再使旧单元与旧资源占用失效并保存新版本；失败则全部回滚，旧安排保留。取消和明确核实的爽约释放有效占用但保留历史。治疗延长通过同一校验流程，后续时段或资源冲突时拒绝延长，前台先协调受影响预约。

新增资源停用区间不会自动取消患者预约。资源协调页列出重叠的待到诊或已到诊记录，前台据此联系患者；接诊入口重新检查资源是否可用。降低容量或直接停用会破坏已有占用时拒绝普通参数变更。误签到在尚未建立就诊时可经前台记录核验依据后纠正；已经接诊须走受控更正。

## D6 患者身份与联系方式

患者UUID是稳定身份，手机号是有索引的可变联系方式，已取消唯一约束。相同手机号或姓名与出生日期匹配仅提供重复提示，不自动合并、不转移病历，也不据此判定新客优惠资格。自助注册形成独立待核验档案；前台先建档后，可在本人核验入口关联未占用账号或创建新的自助账号。

本人核验保存核验岗位、时刻及审计依据。手机号变更由前台核验后办理，患者身份与原就诊关系保持不变；姓名或出生日期修改会使旧身份核验失效。账号已关联其他档案时拒绝直接绑定。跨诊所手机号查询仅显示基础识别信息，不开放病史、联系人和账单地址。

辅助人员以诊所容量池表示，尚未实现具体护士身份、跨店个人排班和资质组合。团购外部核销、真实支付与退款不属于本演示实现；付款为模拟记录。项目性能目标仍须单独测量，不能由功能测试推定。

## D7 经营统计口径

采用自然季度，收入按成功收款时刻归属，成本按发生日归属。医疗用品与运营费用分别汇总；未归属医生的公共费用单列，不自动分摊。医生报表显示扣除直接成本后金额，不将其称为个人净利润。全连锁季度基金为max(管理口径净利润,0) × 10%，四舍五入至分，个人分配规则尚未确定。

取消率与爽约率使用同一到期预约范围，按首个单元开始时刻归入季度、按计划治疗结束判断到期；旧记录无方案时使用首单元结束。未确认到期记录保持待核对，不自动记为爽约。利用率按全部连续时段关联统计，分子为已到诊或已完成预约关联的到期单元，分母为已结束的有效排班单元。

## D8 三层结构与岗位状态控制

表现层由模板、HTML、CSS与JavaScript构成，视图接收请求并组织页面；业务逻辑层由事务服务统一校验状态、权限、金额和资源冲突；数据访问采用Django ORM与PostgreSQL约束。重要操作在服务端重新校验，界面是否显示按钮不作为最终授权依据。

| 角色 | 主要操作和数据范围 | 业务状态约束 |
| --- | --- | --- |
| 患者 | 本人档案、预约和关联记录 | 自助取消须满足提前时间与待到诊状态 |
| 前台 | 所属诊所建档、代约、签到、出单和模拟收款 | 未签到不进入接诊；未完成就诊不出单 |
| 医生 | 本人接诊、治疗记录、申请更正和业绩 | 治疗进行中可编辑；完成后走受控更正 |
| 诊所管理者 | 所属诊所排班、资源协调和更正审批 | 审批与申请分工；变更不得破坏有效占用 |
| 总部 | 跨诊所基础资料与经营汇总 | 按全局授权读取，历史价格快照保留 |
| 财务 | 授权诊所成本、费用核对和结算办理 | 作废与模拟付款仅针对未支付有效单据 |
| 系统管理员 | 账号、角色与授权范围及运行审计 | 技术管理不自动取得病历和经营明细权限 |

一个账号可有多项RoleAssignment，每项授权记录角色、本人或诊所或全局范围以及有效期。Role.permissions提供角色与权限的多对多映射；现有业务入口主要按角色代码与数据范围执行校验，动态权限配置引擎尚未实现。出单和作废等共享操作保存实际办理账号、时间及审计；前台办理与财务复核的职责在需求规约中分别定义。

界面根据岗位范围及业务状态显示操作。预约、就诊和结算详情中，有权限但条件不满足的操作灰置，并显示时间、状态、资源或审批原因；确认页同步提示。患者仅见本人允许办理的入口，直接访问办理地址仍检查岗位和数据范围。最终提交在事务中重新核验，避免状态变化或绕过界面造成错误办理。
